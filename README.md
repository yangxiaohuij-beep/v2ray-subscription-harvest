# v2ray-subscription-harvest · 订阅节点收割流水线

从 GitHub 上自动发现、抓取、分类、测速、打分并打包免费订阅源（vless / vmess / trojan / ss / ssr / hysteria2 / tuic / wireguard），
每天产出一份可直接导入 v2rayN 的节点包，以及一份「按可用性排序」的订阅源清单。

本仓库是该流水线的**完整交付物**：需求 → 可行性 → 架构 → 详细设计 → 运维手册 → 数据质量报告，
加上全部源码、当日产出与数据快照。

> ⚠️ 本项目**不运营任何节点**，只做公开信息的收集与测量。节点全部来自第三方公开仓库/站点，可用性、安全性与合法性由源站负责。
> 使用者需自行遵守所在国家/地区的法律法规。详见文末「免责声明」。

## 它解决什么问题

免费订阅源的现实：

- 散落在成百上千个 GitHub 仓库里，靠人肉收藏，断更、删库、换成图片、塞广告都很常见；
- 「能下载」不等于「能用」：大量链接返回的是 HTML 页面、死链、占位示例，或者早就没在维护；
- 单个源随时会挂，用一个源就是拿整个客户端赌运气。

本流水线的做法：**每天把「仓库 → 链接 → 配置 → 端点」这条链路整条重走一遍，用可测量的指标给每个源打分**，
最后产出「少量、但整体更可靠」的订阅包，而不是一份几千条死链的大杂烩。

## 工作原理（五阶段流水线）

```
search  →  collect  →  prove  →  write  →  rebuild+export
GitHub搜索   抓README    抓链接测TCP   淘汰/排序     重建包/转v2rayN
```

| 阶段 | 做什么 | 关键判据 |
|---|---|---|
| **search** | 12 组关键词 × 2 页调用 GitHub Search API，仓库清单写入 `rapo.txt` | 已认证时 2.5s/页，未认证 7s/页，403 退避 60s |
| **collect** | 逐仓库抓 README（raw，镜像优先）；无 README 猜常见路径；可选扫文件树 | 只认 `http(s)` 链接，过滤占位符/媒体后缀/无意义路径 |
| **prove** | 逐个链接抓取并分类：`configs` / `catalog` / `html` / `empty` / `dead`；对配置类抽样做 TCP 握手 | **≥2 条配置**才算订阅（README 里顺带提一条不算） |
| **write** | 按打分公式重算所有源分数，退役 14 天无响应的源，重写 `subs/all.txt`（分数降序） | 退役只记录到 `retired.txt`，不删前科 |
| **rebuild+export** | 用 `all.txt` 的存活源重建 bundles，再转成 v2rayN 的 best/mini/sources | 增量模式下这一步是保证「当日包是当日数据」的关键 |

打分为可达性优先（延迟只作 tiebreak）：

```
score = 100 × (0.34·reach + 0.20·fresh + 0.14·clean + 0.12·speed + 0.12·volume + 0.08·modern)
```

## 快速开始

### 1. 准备

- macOS / Linux，Python **3.9+**（纯标准库，无需 pip 安装任何依赖）
- 可选：`gh` CLI 已登录 → 自动注入 `GITHUB_TOKEN`，搜索阶段从每页 7s 降到 2.5s

### 2. 部署（扁平目录）

六个脚本必须放在**同一个工作目录**里（脚本以自身所在目录为运行目录）：

```bash
mkdir -p ~/harvest && cd ~/harvest
cp /path/to/repo/scripts/* .
./run_daily.sh            # 增量：搜索→收集→重证新链接→重写 all.txt→重建 bundles→导出
MODE=full ./run_daily.sh  # 全量：把全部候选重新证一遍（约 16 分钟）
./run_full.sh             # 全量的后台启动器（nohup，秒级返回，供定时任务调用）
```

可用环境变量覆盖默认值：

| 变量 | 作用 | 默认 |
|---|---|---|
| `HARVEST_RUN_DIR` | 运行目录 | 脚本所在目录 |
| `HARVEST_PYTHON` | Python 解释器 | `/usr/bin/python3` |
| `HARVEST_GH` | `gh` 可执行文件（用于取 token） | `/opt/homebrew/bin/gh` |
| `HARVEST_NO_PROXY` | 设为 1 强制直连，忽略系统代理 | 未设置 |

### 3. 产出

```
out/
  v2rayN-<日期>-best.txt            明文，≈2000 条，跨源去重后的最优集
  v2rayN-<日期>-best-base64.txt     base64 整包（剪贴板导入用）
  v2rayN-<日期>-mini.txt            100 条，跨协议轮询，体积小
  v2rayN-<日期>-mini-base64.txt     base64 版
  v2rayN-<日期>-sources.txt         ≈2800 个订阅源 URL（订阅设置里可长期自动更新）
  freev2rayu-<日期>.txt             附加源（Free V2rayU 站点）的当日存活节点
  freev2rayu-<日期>-base64.txt      base64 版
subs/
  all.txt            存活订阅源清单，分数降序（客户端「自动模式」直接吃这个文件）
  status.json        每个链接的测量记录（分数、可达率、延迟、摘要、上次存活时间）
  candidates.txt     候选链接池
  retired.txt        退役记录
  bundles/           all/mini/lite/medium/按协议/reality/tls/best + 各自 base64
```

### 4. 导入 v2rayN

- **离线（推荐首次）**：打开 `out/v2rayN-<日期>-best-base64.txt` 全选复制 → v2rayN 主界面「从剪贴板导入批量URL」
- **在线（可长期自动更新）**：把 `out/v2rayN-<日期>-sources.txt` 里的地址逐条加进「订阅设置」

`mini` 包是为「只想快速起步」准备的：100 条，跨协议轮询 + 同一主机最多 2 条，避免被单一源/单一协议绑死。

## 每日实测（示例）

| 日期 | 模式 | 阶段耗时 | 存活源 | 端点/配置 | best 包 |
|---|---|---|---|---|---|
| 2026-10-28 | 增量 | 221s | 1664 | 1118 配置 | 1995 条 |
| 2026-10-30 | 全量 | 961s | 2810 | 64260 配置 | 1996 条 |
| 2026-11-01 | 增量 + 重建 | 199s + 87s | 2804 | 76400 端点 | 1999 条 |

全流程（含附加源）实测约 **7 分钟**。全量重证约 **16 分钟**（`--workers 40 --timeout 8`）；
若用默认 16 并发 25s 超时，同样工作要 9 小时——瓶颈全在死链等超时，不在算力。

## 设计上几个刻意的取舍

1. **排序看可达性，不看延迟**：实测「按 ping 排」比随机更差，最快的响应者往往是 CDN 边缘，背后是死主机。
2. **≥2 条配置才算订阅**：README 里顺带写一条 URI 太常见，一条不配被收录。
3. **摘要用解码后文本算**：base64 源每次构建会重新编码，用原始字节摘要会把「没变化」误判成「每日更新」。
4. **退役不删除**：只记 `retired.txt`，源回归时还能认出它，不丢前科。
5. **增量必须配全量**：`--only-new` 不刷新老链接的 `lastAlive`，纯增量跑 14 天后老源会集体退役。
6. **增量之后一定要重建 bundles**：否则当日包只是把上一次全量的 bundles 重新导出一遍（文件名是新的，内容是旧的）。

## 已知局限

- 只测 **TCP 可达 + 抽样延迟**，不验证协议握手、TLS 指纹、流量是否被劫持 —— 高分源也可能随时失效或不可信。
- 打分是「几分钟内可测量的东西」，不衡量隐私政策、日志留存、带宽上限。
- 国内网络下 `raw.githubusercontent.com` 常挂（SYN_SENT），依赖镜像回退；镜像本身也可能失效。
- 系统代理开着但节点已死时，Python 的 urllib 会集体 SSL EOF（curl 却正常），见 `docs/05` 故障树 F-04。
