---

## 1. 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| 候选池规模 | `candidates.txt` 行数 | 覆盖面是否在扩大 |
| 存活源数 | `all.txt` 行数（`kind=configs` 且 `configs≥5`） | 主要供用户订阅的源数量 |
| 携带配置率 | `kind=configs` / 已测量链接 | 衡量候选池「噪声比例」 |
| 端点总量 | bundles 的唯一 `host:port` 数 | 包的「容量」 |
| 抽样可达率 | `reachRatio`（每源 12 个端点 TCP 握手成功占比） | 源的质量主指标（权重 0.34） |
| 延迟中位数 | 达标端点的 `medianLatencyMs` | 仅作 tiebreak（权重 0.12） |
| 分数分布 | `score` 的分位数与 ≥85 数量 | 决定 best 包容量 |
| 日环比 | 各指标相对前一日的变化 | 判断系统是否健康 |

## 2. 当前快照（2026-11-01）

### 2.1 链接分类（7,612 条已测量记录）

| kind | 数量 | 占比 | 含义 |
|---|---|---|---|
| `configs` | **3,097** | 40.7% | 真的返回 ≥2 条配置 |
| `dead` | 1,805 | 23.7% | 死链 / 4xx-5xx |
| `html` | 1,031 | 13.5% | 返回网页（最常见：仓库首页、404 页面伪装 200） |
| `catalog` | 647 | 8.5% | 链接的链接（页内 ≥3 个订阅链接） |
| `other` | 584 | 7.7% | 文本但不含配置（说明文档、规则文件） |
| `clash` | 442 | 5.8% | Clash YAML（本项目不解析其内部节点） |

> 注意这张表的分母是「历史累计测过的链接」，被良好维护过的源会反复通过，因此 `configs` 占比会随运行天数上升。
> 若看**单次全量**的原始噪声：2026-10-30 全量重证 15,139 个候选，只有 3,091 个携带配置 —— **约 20%**。

### 2.2 存活源与质量分布（3,097 个 configs 源）

| 指标 | 数值 |
|---|---|
| 抽样可达率 reachRatio | 均值 **0.339**，中位数 **0.250** |
| 延迟（达标端点） | 中位 **219ms**，p10 173ms，p90 412ms |
| 分数 | 均值 **55.1**，中位 **55.9** |
| 分数 ≥85（进 best） | **34 个源** |
| 分数 ≥90 | 3 个源 |
| 进入 `all.txt`（configs ≥5） | **2,804 个源** |

**两个直接结论**

1. **能用的源是少数**：只有 34 个源（1.1%）进入 best 档；这也解释了为什么 best 包稳定在 2000 条 —— 受「单源最多 600 条」限制，34 个源 × 最多 600 ≈ 2 万条里再按端点去重、按分数截断。
2. **reachRatio 中位数只有 0.25**：即使是「确认携带配置」的源，抽样 12 个端点里通常也只有 3 个能握手。这是免费源的常态，也是「多源聚合」比「单源订阅」稳的根本原因。

### 2.3 Top 5 源（2026-11-01）

| 分数 | 配置数 | reach | 延迟 | 源 |
|---|---|---|---|---|
| 91.68 | 397 | 1.00 | 262ms | `kort0881/vpn-vless-configs-russia` (githubmirror) |

**洞察**：满分源的特征是 **reach=1.0 + 稳定更新 + 配置量大**，而不是延迟最低（它们都不是 60ms 级）。
这反过来验证了「按延迟排序是错的」这一设计前提。

## 3. 近期运行数据（趋势）

| 日期 | 模式 | 阶段耗时 | 候选池 | 存活源 | 端点/配置 | best 包 | 协议结构（best） |
|---|---|---|---|---|---|---|---|
| 2026-10-27 | 全量 | 26 分钟* | 7,302 | 1,664 | 10,353 | 1,995 | vless 为主 |
| 2026-10-28 | 增量 | 221s | 7,392 | 1,664 | 1,118 | 1,995 | vless 1157 / trojan 733 / ss 105 |
| 2026-10-30 | 全量 | 961s | 15,139 | 2,810 | 64,260 | 1,996 | trojan 1082 / ss 468 / vless 433 |
| 2026-10-31 | 增量（**未重建**，事故） | 206s | 7,449 | 2,811 | 70（塌陷） | 1,996（与 10-30 相同 md5） | 同 10-30 |
| 2026-10-31 | 手动重建 | 157s | — | 2,811 | 76,085 | 1,999 | trojan 977 / ss 545 / vless 464 |
| **2026-11-01** | 增量 + 重建 | 199s + 87s | 7,577 | 2,804 | **76,400** | 1,999 | ss 1039 / vless 514 / trojan 443 |

\* 10-27 为默认并发/超时口径下的早期全量，之后统一改为 `--workers 40 --timeout 8`。

### 3.1 从趋势里读出的三件事

1. **端点总量两周内 1 万 → 7.6 万**：主要来自 10-30 全量把候选池从 7k 扩到 15k（新增仓库 + 老源复活），以及重建步骤把「历史存活源的全部配置」都捞了回来。
2. **协议结构每天在洗牌**：best 包的主协议三天内从 vless → trojan → ss。这不是 bug，而是下游源本身的供给在变；`mini` 包的跨协议轮询正是为此设计。
3. **10-31 的「塌陷」是事故样本**：增量只证到 2 个链接 → bundles 70 条配置。这条曲线证明「增量之后必须重建」不是可选优化，而是可用性底线。

## 4. 质量评估方法（可复现）

### 4.1 「当日包是不是当日数据」

```bash
md5 out/v2rayN-$(date +%Y%m%d)-best.txt out/v2rayN-$(date -v-1d +%Y%m%d)-best.txt   # 必须不同
grep -m1 Generated subs/bundles/index.txt                                          # 必须是今日
grep -c "://" out/v2rayN-$(date +%Y%m%d)-best.txt                                  # 与日志自报一致
```

### 4.2 「分数算得对不对」

任取一条记录，用 `04-详细设计.md` §2.7 的公式手算：

```
reach 0.339×0.34 + fresh 1.0×0.20 + clean …×0.14 + speed …×0.12 + volume …×0.12 + modern …×0.08
× 100  → 应与 status.json 的 score 误差 < 0.05
```

### 4.3 「包里的节点能不能用」（抽检）

```bash
# 从 best 包里抽 20 条，取端点做 TCP 握手，统计成功率
python3 - <<'PY'
import random, socket, re
uris=[l for l in open('out/v2rayN-$(date +%Y%m%d)-best.txt') if '://' in l]
PY
```

抽样经验值：best 包（分数 ≥85 的源）端点可达率显著高于全站均值（全站 reachRatio 中位 0.25）。

## 5. 已知偏差与局限

| 局限 | 影响 | 缓解 |
|---|---|---|
| 只测 TCP 握手，不验证协议层 | 「能连上」≠「能翻墙」，可能被中间设备重置 | best 包优先取 reachRatio=1.0 的源；后续可加协议探测 |
| 延迟是 TCP 握手时间 | 不代表实际带宽/吞吐 | 权重仅 0.12，只做 tiebreak |
| 抽样 12 个端点 | 大源的 reachRatio 有抽样误差 | 大源配置数多，样本相对稳定；必要时 `--samples` 提高 |
| 不评估隐私与日志政策 | 高分源也可能是蜜罐 | README 明示风险；使用者自担 |
| 只覆盖 GitHub 生态 | 频道类（Telegram）源覆盖不足 | 已知缺口；附加源是补丁之一 |
| 增量模式不刷新 `lastAlive` | 需依赖周期全量 | `--max-stale-days 14` + 周全量 |
| 端点去重会丢弃同机多协议 | 包内协议多样性略降 | 换取包体积与导入速度 |

## 6. 改进路线（按性价比）

| 优先级 | 改进 | 预期收益 | 成本 |
|---|---|---|---|
| 高 | 增量阶段对**已有源**也做 3 个端点的轻量复测，刷新 `lastAlive` | 降低对周全量的依赖，源老化更快被发现 | 中（每日 +1~2 分钟） |
| 中 | 重建只抓 top-N（`--limit 800`） | 重建 87s → ~30s，best 质量几乎不变 | 低 |
| 中 | 对 best 前 200 条做协议握手探测 | 「导入即可用」比例显著提高 | 中 |
| 低 | `status.json` → SQLite | 支撑更长历史、更快重算、可做趋势图 | 中 |
| 低 | 源贡献度分析（哪些仓库长期贡献最多节点） | 优化搜索关键词与仓库池 | 低 |
