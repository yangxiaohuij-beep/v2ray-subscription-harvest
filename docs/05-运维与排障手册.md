## 1. 部署

### 1.1 机器要求

| 项 | 最低 | 实测环境 |
|---|---|---|
| OS | macOS 12+ / Linux | macOS 27（Apple Silicon） |
| Python | 3.9+（标准库齐全） | 3.9.6 / LibreSSL 2.8.3 |
| 内存 | 512MB 可用 | 16GB，任务峰值 RSS ≈ 40MB |
| 磁盘 | 300MB | status 4MB + bundles 103MB + out 7MB/周 |
| 网络 | 能访问 github.com / api.github.com | 郑州联通家宽，raw 域名需镜像 |

### 1.2 安装步骤

```bash
# 1) 建目录并放脚本（必须扁平：6 个脚本 + 数据目录在同一层）
mkdir -p ~/harvest && cd ~/harvest
cp /path/to/repo/scripts/* .

# 2) 首次初始化（全量，约 16-25 分钟；也可先跑 daily 看小规模结果）
./run_daily.sh              # 首次没有 rapo.txt 也能自举：search → collect → prove
# 建议首次直接跑全量：
MODE=full ./run_daily.sh

# 3) 验证产物
ls out/ subs/bundles/
```

> 首次运行没有 `subs/` 也会自动创建；`--only-new` 在空状态下等价于全量，因此**首次务必不带 `--only-new`**（`run_daily.sh` 的 daily 模式会带上，所以首次用 `MODE=full` 更稳）。

### 1.3 认证（可选但强烈建议）

```bash
gh auth login            # 或 export GITHUB_TOKEN=<token>
```

`run_daily.sh` 会在启动时 `gh auth token` 取一次并注入环境变量，**不落盘**。
效果：搜索阶段每页等待 7s → 2.5s，全量耗时约降 30%。

## 2. 调度

### 2.1 Hermes cron（本机现用方案）

| Job ID | 时间 | 内容 | 关键设置 |
|---|---|---|---|
| `d89f673b8273` | 每天 07:00 | 日跑（增量+重建+导出+附加源） | `no_agent=true`，脚本 `subscribe-harvest-daily.sh` |
| `ea725a6a404a` | 每周日 04:00 | 全量重证 | 调用 `run_full.sh`（nohup 立即返回） |

`HERMES_HOME/scripts/subscribe-harvest-daily.sh` 只是一层薄包装：

```bash
#!/bin/bash
exec /bin/bash "/Users/mac/word/订阅节点运行/run_daily.sh"
```

**为什么必须是 `no_agent=true`**：脚本型任务一旦走 agent 阶段，会被「全局模型漂移 → drift_skip 静默跳过」影响，
既不投递也不通知（故障树 F-05）。`no_agent` 模式下脚本 stdout 逐字投递，因此**摘要格式由脚本自己保证**。

### 2.2 crontab 替代

```cron
0 7 * * *  cd /Users/mac/harvest && ./run_daily.sh >> logs/cron.log 2>&1
0 4 * * 0  cd /Users/mac/harvest && ./run_full.sh
```

### 2.3 launchd 替代（macOS）

```xml
<key>StartCalendarInterval</key>
<dict><key>Hour</key><integer>7</integer><key>Minute</key><integer>0</integer></dict>
<key>ProgramArguments</key>
<array><string>/bin/bash</string><string>/Users/mac/harvest/run_daily.sh</string></array>
```

### 2.4 机器关机会怎样

- 调度器错过时间窗后通常会在「下次可用时补跑」（Hermes 的宽限为 7200s）；
- **但关机一整天就补不上了**（2026-10-29 整天未跑，10-30 开机补跑时又被杀，导致连续两天无新数据）；
- 建议：给机器设「定时唤醒」（`pmset repeat wakeorpoweron`）+ 保持 Hermes 桌面 App 运行；
  或直接把任务放到一台常开的小机器上。

## 3. 日常巡检（每天 1 分钟）

```bash
cd ~/harvest
# 1) 今天的产物在不在、是不是新的
ls -la out/ | grep "$(date +%Y%m%d)"
# 2) 主包是否真的换了内容（最关键的一条）
md5 out/v2rayN-$(date +%Y%m%d)-best.txt out/v2rayN-$(date -v-1d +%Y%m%d)-best.txt
# 3) bundles 是否今日生成
grep -m1 Generated subs/bundles/index.txt
# 4) 日志尾部有没有 ⚠️
grep -n "⚠️" logs/daily-$(date +%Y%m%d).log
```

判定标准：

| 观察 | 结论 |
|---|---|
| 两个 md5 相同 | ⚠️ 当日包是旧数据（F-02 或 F-01） |
| `index.txt` 的 `Generated` 不是今日 | 重建没跑 |
| 日志出现「跳过 v2rayN 导出」 | 采集失败（F-01） |
| 出现「重建 rc=3」 | 源大面积失效（此时保留旧包是正确行为，需人工查） |

## 4. 故障树

### F-01 采集被 SIGTERM 杀掉（rc=143）

**签名**

```
run_daily.sh: line 61: 802 Terminated: 15  "$PY" -u harvest_lite.py daily ...
状态: daily rc=143, bundles 重建 rc=99, 导出 rc=99
```

**根因**：调用方（调度器 / 工具层 / 终端会话）对进程组发 SIGTERM。历史事故里 22 分 38 秒被杀，
但同期脚本本身无超时逻辑、Hermes 日志无 pre-run 超时记录、kernel 无 jetsam —— 属于「外部超时」。
诱因常见于：机器刚开机（负载 15 分钟均值 11+）、网络劣化（大量重传）导致同一工作量耗时翻数倍。

**处置**

1. 立刻看 `logs/daily-<日期>.log` 停在哪个阶段（停在 `[320/772]` 这类进度 → 是 collect 阶段被杀）；
2. 确认 `subs/` 时间戳是否为今日 —— 若未更新，则本次**什么都没写进去**；
3. 手动补跑：`cd ~/harvest && ./run_daily.sh`（或 `MODE=full ./run_daily.sh`）；
4. 想彻底规避：让任务脱离调用方进程组（`nohup`），见 `run_full.sh` 的做法。

> 已实现的护栏：采集失败时**跳过导出**（rc=99），不会再生成「看着齐全、其实全是旧数据」的当日包。

**2026-11-26：机制已确认。** 这次调度器把原因写进了执行记录：

```
status=failed  error: Script timed out after 3600s: .../scripts/subscribe-harvest-daily.sh
07:00:23 开始 → 08:00:24 被杀（整 60 分钟）
```

当天工作量暴涨：仓库 1031 个、候选 **8265**（平时 ~4.9k）、待证新链接 **3411**（平时 6~101）；
collect 已吃掉 44 分钟，prove 跑到 2500/3411 时撞上 3600 秒上限。根因是「退役→从 status 移除→
次日又被 collect 收回当新链接」的死循环把候选池吹大（`retired.txt` 已 9346 条，`status.json` 只剩 4854 条）。

**已上的两条护栏（v1.1）**

| 护栏 | 参数 | 作用 |
|---|---|---|
| 每轮新链接上限 | `--max-new 600` | 单轮证明量可预期，日跑耗时不随候选池波动 |
| 退役源静默期 | `--retired-days 30` | collect 不再把 30 天内退役的 URL 收回重证，斩断死循环 |

补跑方法（跳过已完成的 search/collect，只做 prove→write→重建→导出→附加源）见 `logs/catchup-*.log` 与
仓库里的 `catchup_<日期>.sh`（2026-11-26 实测 1840 秒完成，产出与其他日期一致）。

### F-02 当日包与前一日 md5 完全相同

**根因**：增量模式（`--only-new`）只重证新链接，`write_bundles()` 手里只有几十条配置，
而 `make_v2rayn.py` 读的 `bundles/best.txt` 本轮没被重写 → 导出的是上一次全量的内容。

**处置**

1. 确认是不是这个原因：`bundles/index.txt` 显示配置数只有几十条（正常应是几万）；
2. 手动重建：`python3 rebuild_bundles.py --workers 40 --timeout 8`，再 `python3 make_v2rayn.py subs/bundles out`；
3. 长期：`run_daily.sh` 已内置「导出前重建」，若仍出现说明重建 rc≠0，查 `⚠️ bundles 重建 rc=` 行。

### F-03 `SSL EOF` / `curl 通、Python 全挂`

**签名**

```
首页抓取失败: URLError(SSLEOFError(8, 'EOF occurred in violation of protocol (_ssl.c:1129)'))
```

且 python 对**任意** https 域名都瞬断（0.0s），而 `curl -sSI <同域名>` 返回 200。

**根因**：macOS 系统代理开着（`scutil --proxy` 显示 HTTP/HTTPS/SOCKS 指向 `127.0.0.1:10808`），
`urllib` 读系统代理走本地代理；代理进程活着但**节点已死**，CONNECT 先回 200 再立刻断开 → TLS 拿到 EOF。
`curl` 只读环境变量不看系统代理，所以表现不一致。

**诊断三步**

```bash
scutil --proxy
python3 -c "import urllib.request;print(urllib.request.getproxies())"
python3 -c "import urllib.request as u;print(u.build_opener(u.ProxyHandler({})).open('https://api.github.com/').status)"  # 200 = 直连可行
```

**处置**：脚本已内置探测（探 4 秒不通即直连）；应急可 `HARVEST_NO_PROXY=1 ./run_daily.sh`。

### F-04 采集「卡住」不动，CPU 几乎不涨

**根因**：`raw.githubusercontent.com` 国内不可达，连接停在 `SYN_SENT`，每请求都等满超时。

**诊断**

```bash
lsof -p $(pgrep -f harvest_lite) -a -i | head      # 大量 SYN_SENT
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://raw.githubusercontent.com/  # 挂住/超时
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://api.github.com/            # 200
```

**处置**：脚本默认镜像优先（gh-proxy.com → ghproxy.net → ghfast.top → jsdelivr），坏的镜像本次会话拉黑；
若全部镜像也失效，只能换网络或等镜像恢复。

### F-05 定时任务「没报错也没产出」

**根因**：agent 模式的 cron 遇到全局模型漂移会 `drift_skip` 静默跳过，不投递不通知。

**处置**：脚本型任务一律 `no_agent=true`；若必须走 agent，就显式 pin 模型。
已知：Hermes 0.21.0-cn.18 的 `cron edit` 没有 `--provider/--model` 参数，需改 `cron/jobs.json`。

### F-06 摘要里出现 `STAMP（: unbound variable`

**根因**：macOS 自带 bash 3.2 会把全角括号的 UTF-8 首字节当成变量名字符。

**修法**：`echo "... ${STAMP}（${LABEL}）"` —— 变量一律加大括号。

### F-07 老源集体退役、`all.txt` 突然变短

**根因**：`--only-new` 不刷新老链接的 `lastAlive`，14 天后被退役规则清掉。

**处置**：`MODE=full ./run_daily.sh` 跑一次全量；长期看保证「每周至少一次全量」。

### F-08 重建后包变小很多

**根因**：源整体失效 / 网络导致大量抓取失败 / `--per-source` 或 `--limit` 被改小。

**处置**：看重建日志 `抓完：X/Y 个源有配置`。
- 若 X/Y 明显偏低（如 < 60%），先查网络（F-03/F-04）而不是改参数；
- `min-total` 保护会在唯一端点 < 500 时直接放弃写入，此时 `out/` 保持上一次的包。

## 5. 备份与恢复

| 对象 | 建议 | 说明 |
|---|---|---|
| 脚本 | 纳入 git（本仓库） | 唯一需要版本管理的东西 |
| `subs/status.json` | 每周备份一次 | 丢了等于所有源「重新做人」，历史分数与 lastAlive 全清零 |
| `subs/all.txt` | 随 status 一起 | 客户端订阅直接用这个文件 |
| `out/` | 不必备份 | 随时可由 bundles 重新导出 |
| `subs/bundles/` | 不必备份 | 可重建（`rebuild_bundles.py`） |

```bash
# 备份
tar czf ~/harvest-backup-$(date +%Y%m%d).tgz -C ~/harvest subs/status.json subs/all.txt subs/retired.txt rapo.txt
# 恢复
tar xzf harvest-backup-YYYYMMDD.tgz -C ~/harvest
```

## 6. 升级流程

1. 拉取本仓库 `scripts/` 到临时目录；
2. 对比 `diff -u` 你正在跑的脚本，确认没有本地私有改动被覆盖；
3. 替换后先跑 `bash -n run_daily.sh`、`python3 -m py_compile *.py`；
4. 在沙箱里跑一次（把脚本放进临时目录，桩掉 Python）确认编排顺序；
5. 手动 `./run_daily.sh` 一次，确认产物正常，再交给定时器。

## 7. 性能调优速查

| 想解决的问题 | 动作 | 预期 |
|---|---|---|
| 全量太慢（16 分钟） | 提高 `--workers` 到 64、`--timeout` 降到 6 | 约 −25%；注意本机与其他任务的争抢 |
| 每日想更快 | `rebuild_bundles.py --limit 800` | 重建 87s → 约 30s，best 包几乎不变 |
| 想减少带宽 | `--per-source 200`、`--max-bytes 262144` | 配置总量下降，包略小 |
| 机器常年低配 | `--workers 16 --timeout 12` | 全量约 40 分钟，但 CPU/网络更温和 |
| 判断「源在减少」 | 对比 `all.txt` 行数趋势与 `retired.txt` 增速 | 见 `06-数据质量与评测.md` |

## 8. 常见问答

**Q: 每天跑，GitHub 会不会封我？**
A: 搜索 API 有严格 sleep 与 403 退避；raw 抓取走镜像，对 GitHub 主站压力很小。认证后是 30 req/min 的下限，远低于限制。

**Q: 为什么 best 包不是「最全」的包？**
A: best 只取分数 ≥ 85 的源、上限 2000 条。要全量请用 `bundles/all.txt`（约 7.6 万条），但客户端导入会很慢。

**Q: 我把 `subs/all.txt` 直接粘进客户端可以吗？**
A: 可以，这正是「自动模式」的用法；客户端会按顺序尝试。`bundles/best.txt` 相当于「已经帮你筛过一遍」的版本。

**Q: 附加源为什么不并进主包？**
A: 主包只依赖 GitHub 生态，保证可复现；附加源是单站点，故障域不同，混在一起会让「主包是否可用」变得不可判断。
