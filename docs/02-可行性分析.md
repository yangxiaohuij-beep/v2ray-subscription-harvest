# 可行性分析

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0（2026-11-01） |
| 分析对象 | 订阅源自动收割流水线 |
| 数据来源 | 2026-10-27 ~ 2026-11-01 本机实测日志（同一台 macOS，郑州联通家宽） |
| 结论 | **可行**，已在生产环境连续运行并产出可用结果 |

---

## 1. 问题是否值得做（必要性）

先看不做会怎样。下表是实测的「候选链接存活漏斗」（2026-11-01 全量口径）：

| 环节 | 数量 | 留存率 |
|---|---|---|
| GitHub 命中的仓库 | 808 | — |
| 从 README/路径提取的候选链接（累计） | 7577 | — |
| 本次需重证的链接 | 2804（`all.txt` 全量存活源） | — |
| 其中真正返回配置（≥2 条） | 2798 | 99.8%* |
| 抓到的唯一端点 | 76400 | — |
| 抽样端点 TCP 可达 | 约 97%（重建阶段未做全量抽测，取全量测结果推算） | — |

\* 这里的 99.8% 是「已被历史筛过的源清单」的存活率；**候选池的原始存活率低得多**：2026-10-30 全量重证 15139 个候选，只有 3091 个携带配置 —— **约 20%**。

也就是说：如果不做筛选，用户面对的是 80% 的噪声。人工无法每天完成这项工作，脚本可以。**必要性成立。**

## 2. 技术可行性

### 2.1 数据源可得性

| 问题 | 实测结论 |
|---|---|
| GitHub Search API 能否覆盖足够多的仓库？ | 12 组关键词 ×2 页即可稳定拿到 700~800 个仓库，且每天有新仓库（10-31 新增 18 个、11-01 无新增） |
| 是否需要认证？ | 不需要，但认证后每页等待从 7s 降到 2.5s；实测未认证也能跑完，只是慢 |
| 订阅链接是否有固定结构？ | 无。这是关键难点：raw / jsdelivr / github blob / 带 `?raw=true` 混用，必须做 URL 规范化 |
| 站点是否稳定可抓？ | 大体可以；`raw.githubusercontent.com` 在国内会挂（SYN_SENT），必须镜像优先 |
| 内容是否可解析？ | 明文、整段 base64、Clash YAML 三种形态并存，需要分类判定 + base64 截尾重解 |

**结论**：数据源可得，但需要三件工程化处理——URL 规范化、镜像回退、多形态分类。均已实现。

### 2.2 关键假设的验证

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 「按延迟排序」是错的 | 对比 ping 排序与随机取样的实际可用率 | 项目沿用上游结论：最快的响应者常是 CDN 边缘，背后是死主机 → **只用延迟做 tiebreak** |
| 「多源交叉」能提高稳定性 | 观察 best 包每日常驻源数量与波动 | 2804 个存活源中每日约有 500~1000 个端点进出，单源消亡不影响整包 |
| 「增量足够覆盖日常」 | 增量阶段每日只发现个位数新链接（10-31: 0，11-01: 2） | 说明搜索维度已接近饱和；但**仍需每周全量**修正 `lastAlive` 漂移 |
| 「TCP 可达即可作为初筛」 | 抽样 vs 端点总量 | 12 抽样/源已能区分源的质量差异（reachRatio 分布在 0~1 之间区分度明显），全量 TCP 代价过高 |

### 2.3 性能可行性（最容易被低估的一项）

| 场景 | 并发/超时 | 实测耗时 |
|---|---|---|
| 全量重证 15139 候选 | 40 并发 / 8s | **961s（16 分钟）** |
| 同等工作量 | 16 并发 / 25s（上游默认） | 约 **9 小时** |
| 增量重证（只证新链接） | 40 / 8s | **199s** |
| 从 2804 个存活源重建 bundles | 40 / 8s | **87s** |
| 附加源（Free V2rayU） | 32 / 2s（TCP 探测） | **29~136s** |

**关键洞察**：瓶颈不是算力，而是**死链等超时**。所以「并发 × 超时」是可调的第一杠杆；
把 timeout 从 25s 压到 8s、并发 16→40，全量从 9 小时降到 16 分钟（≈34 倍）。

**结论**：单机（16GB 内存的家用 Mac）即可日跑，无需服务器、无需分布式。

### 2.4 技术风险与对策

| 风险 | 影响 | 对策（已实现） |
|---|---|---|
| `raw.githubusercontent.com` 国内不可达 | 采集长时间挂起，看似「卡死」 | 4 个镜像自动回退（gh-proxy.com / ghproxy.net / ghfast.top / jsdelivr），坏的本次会话拉黑 |
| 系统代理开着但节点已死 | Python 全部 SSL EOF，curl 却正常 | 启动时探测代理能否真转发，不通则强制直连（`ProxyHandler({})`） |
| base64 源每次重新编码 | 误判为「每日更新」，fresh 分全错 | 摘要改用**解码后文本**的 sha256 |
| 增量模式让 bundles 塌陷 | 当日包 = 昨日包的副本 | 导出前用 `all.txt` 强制重建 bundles（`rebuild_bundles.py`） |
| 任务被外部 SIGTERM | 退出码 143，但旧产物仍在 | 采集失败即跳过导出（rc=99），不发伪当日包 |
| 调度器超时 | 长任务被杀的边界不可控 | 全量用 `nohup` 后台上拉，秒级返回；日跑保持 < 10 分钟 |

## 3. 方案选型

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 现成订阅** | 直接用网上流传的 1~3 个订阅地址 | 零成本、一分钟上手 | 单点依赖、质量未知、随时失效 | 只作为对照基线 |
| **B. 只用大厂聚合包** | 订阅别人做好的「精选包」 | 省事 | 你的判断依据依然为零，且无法排障 | 不采用 |
| **C. 自建收割流水线（本项目）** | 自己发现、验证、打分、打包 | 口径透明、可复现、可调权重、失败可定位 | 需要一台常开的机器、每天几分钟算力 | **采用** |
| D. 自建 + 协议层探测 | 在 C 之上加握手/TLS 指纹验证 | 质量更接近真实可用 | 成本高、对源站不友好、误判率并不显著下降 | 暂不采用（列入后续） |
| E. 商业机场 | 付费订阅 | 稳定 | 与「免费源聚合」目标不同 | 不在范围 |

选择 **C** 的理由：它在「成本—可控性—可解释性」三角上占比最好。
一旦打分口径公开（见 `04-详细设计.md`），任何人都能复现同一份结果——这是本项目区别于「神秘精选包」的核心。

## 4. 经济可行性

| 项 | 估算 |
|---|---|
| 硬件 | 复用既有家用 Mac（0 元增量投入） |
| 网络 | 每日约 300~600MB 下行（2811 源 × 平均 100~200KB + 附加源），按家宽不计费 |
| 云资源 | 0（无服务器） |
| 人力 | 首次建设约 1 人日；日常 0（全自动，故障时 5~15 分钟介入） |
| 存储 | 状态文件 4MB + bundles 100MB + 历史产出（可裁剪） |

对比人工：每天人工筛 2800 个源、70000 个端点，按 1 个源 10 秒计需 7.8 小时/天。**自动化收益极为显著。**

## 5. 合规与伦理可行性

| 关注点 | 本项目的做法 |
|---|---|
| 只抓公开内容 | 全部数据来自 GitHub 公开仓库的 raw 文件与公开静态站，无登录、无付费墙穿透 |
| 遵守限流 | Search API 认证 2.5s/页、未认证 7s/页；403 退避 60s |
| 不伪造流量特征 | 只做 TCP connect 与 HTTP GET，不做协议层伪装探测 |
| 不存储个人数据 | 状态文件只有 URL、时间戳、测量值，无用户信息 |
| 可移除 | README 声明：源站作者可提 issue 申请移除，下个版本生效 |
| 风险提示 | README 与产出文件均声明「不运营节点、仅供技术研究」 |

**合规结论**：作为「公开信息的索引与度量」是可接受的；产出使用者的法律责任不由本项目承担（README 已明确）。

---

## 6. 结论与建议

1. **技术可行**：单机、零依赖、日跑 7 分钟，已在生产环境连续产出可用结果。
2. **经济可行**：增量成本近似为零，替代了每天数小时的人工筛选。
3. **合规可控**：只索引公开信息，提供移除通道，边界清晰。
4. **建议的演进方向**（按性价比排序）：
   - ①（低）给增量也加「抽样 TCP 复测」，让 `lastAlive` 每日刷新，减少对全量的依赖；
   - ②（中）把重建改成「只重建 top-N 源」，把 87s 压到 30s，同时保 best 包质量；
   - ③（中）加协议握手探测（只对 best 包前 200 条），提高「导入即可用」的比例；
   - ④（高）把状态文件从 JSON 迁到 SQLite，支撑更长历史与更快重算。
